# Full review through continuous hosting — September 19, 2026

Reviewed the implementation following baseline commit `e0f584f`, including the
three authorized steps: the host/control contract, continuous simulation hosting,
and live CLI controls. The review covered Core parsing/generation and clocks,
Runtime persistence/migrations/ownership/delivery/logging, CLI/control boundaries,
regression coverage and process probes, schemas/examples, verification scripts,
and current and historical documentation. Historical reports retain their original
findings and follow-ups; this report describes the current assessment.

No production Historian requests were made. All new execution used temporary
simulation-only databases and a fake Historian. The existing generator version,
model schemas, and SQLite schema version 4 are unchanged. This is an engineering
review with regression evidence, not an independent security certification or a
claim that arbitrary filesystem/database corruption has been exhaustively tested.

## Completed work

1. Defined a bounded, versioned, same-user local pipe contract, with explicit
   ownership, shutdown, size limits, deadlines, and lost-response behavior.
2. Added a foreground continuous host. It rotates generation/delivery rounds,
   waits while idle or blocked, preserves SQLite ownership, logs state changes,
   and stops gracefully without cancelling in-flight delivery.
3. Added live admission, inspection, pause/resume, drain/discard cancellation,
   release, and checked generation recovery, plus host status/stop. Commands run
   between rounds and reuse the existing durable lifecycle operations. No direct
   SQLite fallback, automatic command retry, or production transport was added.

See [the operator contract](continuous-host.md) for commands and troubleshooting.

## Remaining concerns for review

### Production blocker: Historian acceptance guarantees

The production adapter is still disabled. HTTP 200 and omitted repeated samples
do not establish a durable, whole-request acceptance contract. The existing
[delivery decision](delivery-recovery.md) lists the required server guarantees.
Nothing in the fake host changes that decision. Uncertain delivery remains stopped
with payloads and ownership retained; there is no automatic replay or forced ack.

### Medium: capacity and long-term retention still need measurement/design

Models and seeded schedules are reconstructed for each generation turn and delivery
claim. The live queue is bounded and indexed independently of acknowledged history,
but retained audit metadata continues to grow. The host limits the entire database
to 100 sessions, including completed/cancelled sessions. Those limits are explicit,
not evidence of production throughput or indefinite unattended operation.

Before high-volume deployment, measure representative model sizes, points/second,
round/control latency, memory, and disk growth. Define archival without losing
ordering high-water marks or recovery evidence. This review did not add caching,
archival, or a performance claim to the three-step scope.

### Operational limitation: controls can have unknown outcomes

One client is serviced at a time; a stalled connection has a deadline. Commands
execute between rounds, so 100 complex sessions can delay a response. Once queued,
a command may commit after its client leaves. There is no durable command receipt
or exactly-once control protocol. The CLI explains this and never retries; inspect
status before reissuing a mutation. A graceful stop acknowledgement is not proof
that the process has already exited. Same-user processes are trusted; current-user
pipe restrictions do not protect against malicious code running as that user.

### Low: broader automation and portability coverage

The repository has reproducible local verification but no CI workflow. Pipe controls
and process shutdown were tested on macOS; Windows/Linux behavior and cross-user
rejection were not independently exercised. Service installation, automatic startup,
and SIGTERM integration remain unimplemented. Local reservations require one
canonical database path and connection profile; they cannot exclude external tag
writers or coordinate aliases across independent databases.

### Maintainability: schema duplication and richer model semantics

The combined schema retains copied primitive definitions across pattern contexts.
Current schema/example checks pass, but duplication can drift as patterns expand.
Refactor with parity tests before extending general expressions and nesting.
General typed conditions, equipment group state, noise/fault quality policies,
production/time totalizers and target completion remain in the Phase 1 plan.
The current pure-pattern checkpoint contract must be extended explicitly for those
stateful behaviors. No additional generator-clock defect was reproduced here.

## Subsequent owner decision: blind publishing

The owner clarified that per-point success receipts and count reconciliation are
unavailable. The former production acceptance-guarantee blocker is superseded by
the [blind-publish policy](delivery-recovery.md): record publish completion, check
relevant arrival/non-null values/expected changes as indicators, and rely on user
feedback for intended behavior. First-in-wins duplicates remain owner-confirmed.
The adapter and monitor still require implementation; uncertainty and no-replay
protections remain. This follow-up changes the design decision, not audit test
results or the current fake-only runtime.
