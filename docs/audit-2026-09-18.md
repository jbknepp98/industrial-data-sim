## Findings

### A1 — Medium: validation error responses bypass the output limit

Location: `src/IndustrialDataSim.Cli/CliApplication.cs`, `WriteResult` at line 129;
`src/IndustrialDataSim.Core/Configuration/SessionDefinitionLoader.cs`,
`CheckProperties` at line 125.

Successful previews use `BoundedJsonBuffer`, but failure responses serialize the
entire collected error list directly to stdout. Error collection itself has no
count limit. This bypasses the advertised response-size protection and allows
small malformed agent inputs to produce disproportionately large responses.

Reproduction: run `dry-run` on a JSON object containing 100000 occurrences of
`"x":0`. The file is 600001 bytes, below the 1 MiB input limit. The process returns
exit code 1 with 100005 errors and 10500634 bytes of stdout, over the 4 MiB cap.
The reproduction printed byte/error counts only, not the oversized response.

Impact: unnecessary allocation and serialization, agent context/log flooding,
and violation of the expected bounded CLI response. No credential disclosure
was observed in this reproduction. The output remains valid JSON.

Recommended fix: bound error collection and use bounded serialization for every
response. Return an explicit diagnostic-truncation indicator or summary while
preserving invalid status and the existing exit contract. Add a regression test
covering oversized diagnostic arrays, not just oversized successful previews.

### A2 — Medium: current contracts contain stale clock and capability claims

Locations: `docs/ramp-simulation-v1.md` lines 48–74 and 98–100;
`docs/constant-simulation-v1.md` opening/version paragraphs;
`docs/session-header-v1.md` introduction;
`docs/staircase-simulation-v1.md` final randomness paragraph.

The ramp contract defines elapsed time exclusively from the session start and
calls local origins future work. That is now false for a ramp inside a Boolean
gate. In the published gate example, at session second 10 the paused ramp is at
4 and the continuing ramp at 8, not 10. The gate contract states the right rule,
but readers must reconcile conflicting descriptions themselves.

The constant contract still describes the combined schema as supporting only
constants and ramps and says random models will introduce seed contracts later.
The header introduction similarly describes sampling and seeds as future work,
without consistently distinguishing the unchanged header from the implemented
wrapper. The staircase document calls randomized output values future work even
though the random-integer pattern now exists. Historical implementation-log
entries are appropriate history; these active reference documents need clearer
current scope.

Recommended fix: explicitly distinguish standalone/session time from the local
clock supplied by composition or gating. Update capability links and status
wording in the active contracts, and retain historical statements in the log.
These documentation corrections should not alter generatorVersion 1 behavior.

### A3 — Delivery design blocker: recovery rules still need a consistent policy

Locations: `docs/phase-1-plan.md`, Milestone 5; `README.md`, Ordering requirement;
`docs/timebase-api-findings.md`, unchanged-value observations.

The plan correctly flags that repeated samples can disappear from read-back,
but then retains an algorithm requiring exact point verification and resending
an absent suffix newer than the latest stored timestamp. That algorithm cannot
be applied unchanged to the observed server behavior.

For example, a constant submitted through 01:59 can still have a latest stored
point at 00:00. Missing repeated points are not evidence that they were never
accepted. A retry based solely on latest stored time can replay earlier
submissions, while strict point-for-point verification can remain unresolved
forever. The warning already acknowledges this; the concrete state/retry policy
has not been resolved.

Recommended decision before implementing delivery: define separate generated,
attempted/submitted, acknowledged, retained-transition-verified, and uncertain
progress. Specify what constitutes sufficient receipt evidence for repeated
samples, when operator intervention is needed, and which retries are permitted
without weakening the forward-only rule. Do not silently substitute transition
verification for proof that each repeated input sample was stored.

This is an acknowledged future-delivery blocker, not a defect in an existing
production writer: no production writer or recovery engine exists yet.

### A4 — Medium: important verification cannot run from a clean checkout

Locations: ignored `.tools/check-*.py`, `.tools/prepare-trigger-check.py`,
`.tools/write-trigger-check.py`; `tests/IndustrialDataSim.Tests`;
`docs/implementation-log.md` verification claims.

The C# regression suite covers substantial generator behavior and includes
independent timing reference vectors. However, schema/runtime comparisons,
several independent full-example oracles, and the live transport/read-back
harness exist only in ignored local tooling. The .NET suite does not run those
schema checks. There is no repository CI workflow to exercise them automatically.

Keeping credentials, certificates, payload dumps, and local manifests ignored
is correct. Keeping all reusable test logic there means another checkout cannot
reproduce the complete verification described in the documentation, even after
the implementation files themselves are committed.

Recommended fix: promote sanitized offline schema/CLI checks and synthetic
fixtures into reproducible test tooling; document and pin its development
requirements. Add an explicitly opt-in live test harness with secrets supplied
externally and fresh-tag safeguards. Keep live artifacts/configuration ignored.
Add CI for offline checks once these files are versioned.

## Additional maintainability and coverage observations

- The combined schema has grown to 942 lines, with copies of primitive patterns
  in top-level, sequence-child, switch-branch, and gate-child definitions. Current
  example checks pass; this is a drift risk, not a demonstrated schema failure.
  Shared canonical definitions and automated structural parity checks would help.
- Pattern dispatch uses contextual Boolean flags and several type-specific
  binding cases. This is understandable at the current restricted scope. Before
  adding arbitrary dependency graphs or nested interlocks, replace implicit
  combinations with explicit supported contexts/dependency contracts.
- The latest pause/continue gate modes have offline verification only. The live
  Boolean test covers restart-on-change sequence switching, not gated output gaps.
  A future live gate test must distinguish no writes from Historian interpolation
  or last-value display behavior; no-point gaps do not imply a chart shows nulls.
- No crash/restart, sustained throughput, backpressure, multi-session ownership,
  cross-process concurrency, or server-restart durability testing is claimed.
  These correspond to unimplemented planned capabilities, not failing features.

## Current scope versus the original project

Implemented: strict offline configuration/CLI, constants, ramps, staircases,
seeded dwell timing, exact-duration random-integer holds, finite sequence
composition, local Boolean switching, and pause/continue suppression. Live
connectivity and generated-data behavior have been demonstrated by local probes.

Still planned: persisted sessions and SQLite queues; ownership/reservations;
concurrent job scheduling; production authentication/transport/recovery;
backpressure and capacity measurement; general conditions and equipment groups;
noise/faults/quality policies; totalizers/production-batch targets; lifecycle
commands and transition/explanation traces. The current deliverable is a tested
offline generator prototype, not the complete Phase 1 resumable simulator.

Recommended order: repair A1; reconcile active contracts and the recovery plan;
make offline verification reproducible; checkpoint the reviewed implementation;
then resume feature development. Preserve the explicitly documented timing and
seed semantics unless a versioned change is intended.
