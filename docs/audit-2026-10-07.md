## 1. P1 — Session integrity failures can terminate the shared worker

**Impact:** a damaged session can interrupt healthy sessions and terminate the
resident host, despite the intended per-session failure isolation. The damaged
session is correctly marked Failed and unsafe data is not submitted; the failure
is the unnecessarily broad operational interruption.

[ProductionWorker.cs:40](../src/IndustrialDataSim.Runtime/ProductionWorker.cs#L40)
catches integrity errors around generation only. For a Draining session,
generation returns without loading the model, and
[ProductionDelivery.cs:40](../src/IndustrialDataSim.Runtime/ProductionDelivery.cs#L40)
loads it outside the guarded preflight block. Its error escapes the whole round.

The simulation path also lacks the new `extension.integrity` case in
[SimulationWorker.cs:77](../src/IndustrialDataSim.Runtime/SimulationWorker.cs#L77)
and [DurableRuntime.Delivery.cs:39](../src/IndustrialDataSim.Runtime/DurableRuntime.Delivery.cs#L39).
Updating `GenerateRound` did not cover the worker's direct `Generate` calls.

**Reproduction:** admit two disjoint sessions; make the first Draining and damage
its saved configuration hash. Production throws `runtime.configuration_integrity`,
marks the first Failed, and leaves the healthy session's cursor at zero. Separate
simulation probes damage horizon metadata in Ready and Draining states; both
throw `extension.integrity` and leave the healthy cursor at zero.

**Recommended repair:** isolate these two explicitly classified session-local
integrity failures across both generation and delivery. Preserve Failed state,
queued payloads and reservations. Continue the healthy session; do not swallow
storage failures, invalid global state or unexpected exceptions. Promote all
three reproductions to permanent regression tests, including Cancelling state
and a resident-host responsiveness check.

## 2. P1 — Publishing after extension/resume does not recheck retention

**Impact:** previously admitted queued values can be submitted outside the
Dataset's current retention window and still become Published/Complete locally.
The audit proves the missing guard and POST; it does not claim to have observed
actual server purging or data loss.

[HistorianClient.cs:56](../src/IndustrialDataSim.Runtime/HistorianClient.cs#L56)
reads Dataset settings and checks purge age at admission. The later
[delivery preflight](../src/IndustrialDataSim.Runtime/ProductionDelivery.cs#L44)
checks connection profile, current tag timestamps and authentication, but does
not refresh/check retention. Extending changes only local horizon state.
The active [extension contract](session-horizon-extension-design.md) says retention
checks still apply before additional publishing; that assurance is too strong.

**Reproduction:** admit a two-day-old range while scripted purge age is 30 days;
change purge age to one day; extend, generate and deliver. The result was
`Published=True`, one settings read total, one POST, and session Complete.

**Recommended repair:** establish an explicit, bounded freshness policy for
Dataset settings before submitting known-unsent work, and validate the pending
batch's actual timestamps against current retention. Do not reuse admission's
original-start check unchanged: a long-running session may have an old origin but
entirely current pending values. Refuse unsafe submissions with an actionable
retention error while preserving the queue; never shift timestamps, discard data
silently or replay Published/Uncertain work. Test changed settings, elapsed-time
expiry, restart/extension, and a valid current batch from an old session.

## 3. P2 — Live status fails when the model is precisely what needs diagnosis

[ProductionHostCommands.cs:156](../src/IndustrialDataSim.Cli/ProductionHostCommands.cs#L156)
always adds `HorizonStatus` to its response. That recompiles/verifies the model;
a model/hash/horizon failure prevents the already available session snapshot and
progress from being returned.

**Reproduction:** mark a session Failed through the existing integrity check,
then execute live status. It returns exit 1 with only
`runtime.configuration_integrity`, omitting the Failed snapshot, cursor, queue and
progress. `production-live list` remains a workaround, so diagnosis is impaired
rather than completely impossible. Related mutation responses can fail during
this post-mutation status assembly even when the mutation already committed.

**Recommended repair:** return safely stored session/progress diagnostics even
when optional horizon/model details cannot be computed. Mark those details
unavailable with their own error. Keep mutation outcome distinguishable from a
subsequent inspection failure. Also reuse the direct production status formatter:
the live endpoint currently emits raw tick counts, whereas direct status emits
readable UTC timestamps.

## 4. P2 — Arithmetic failures give misleading corrective guidance

[ManufacturingDefinitionLoader.cs:478](../src/IndustrialDataSim.Core/Configuration/ManufacturingDefinitionLoader.cs#L478)
passes arithmetic results back into the operand type checker. Consequently,
`1 / 0` reports:

> This expression requires finite numeric operands; implicit conversions are not allowed.

Both supplied operands are finite numbers and no conversion was attempted.
The correct expression path and safe redaction are preserved, but the message
does not explain division by zero or tell the author what to repair. Numeric
result overflow follows the same misleading path. The existing invalid-model
tests mostly check rejection, message length and non-disclosure, missing this.

**Recommended repair:** distinguish operand-type errors, zero denominators and
non-finite arithmetic results with stable codes, the operation path and concrete
guidance. Do not echo raw values. Test the explanation as well as exit status,
absence of partial results and redaction. Note that both `if` branches currently
evaluate eagerly by documented design; suggesting an ordinary conditional guard
alone would not fix an invalid division in its inactive branch.

## 5. P3 — Primary archive documentation is incomplete for the shipped format

[The archive guide](audit-archival.md) describes schema versions 5/6 and the earlier
manifest contents, but omits schema 7, archive format 2, `horizonRevision` records,
batch revision identity, and retention of revisions in SQLite. These are described
elsewhere in the extension guide, leaving the primary operational contract
incomplete. The extension guide's retention claim needs the correction in finding 2.

**Recommended repair:** update the primary archive guide, cross-link the current
extension contract, and distinguish database schema version from export format
version. State that verification compares bytes/hash with the receipt; it is not
an independent replay or semantic revalidation of every exported record.

## Code readability and test coverage assessment

The runtime's separation of durable checkpoints, transport, observations and
operator review is clear. Transaction boundaries, no-replay comments, bounded
outputs, redacted errors and ownership checks are generally well explained.
The existing tests provide useful coverage of deterministic generation, ordering,
crash boundaries and platform behavior. No replay path was introduced by the
failures reproduced here.

The new manufacturing loader is less readable than the surrounding contracts.
It combines shape validation, dependency ordering, precompilation, arithmetic,
state machines and sensor effects in one roughly 500-line class, with frequent
single-letter names and multiple statements on one line. During repairs, separate
validation/typed operations and process execution into focused helpers, use
specific names, and add operation-specific diagnostics. Preserve existing random
streams and timing behavior; avoid combining a broad refactor with semantic fixes.

Coverage gaps are concentrated at component boundaries: new integrity error
codes reaching old workers; expired settings after successful admission; status
inspection of failed models; and explanation quality beyond rejection/redaction.
The six probes below are concrete regression starting points.

The documented process compilation limits, repeated full-horizon compilation,
local-only dependencies, lack of automatic OS service installation, and unresolved
historical control-latency cause remain known limits, not newly proven defects.
No fresh multi-day soak or production capacity measurement was performed here.

## Repair record — October 7, 2026

All five findings are addressed in the working tree:

1. Production model loading and simulation claims isolate both configuration and
   horizon integrity failures after the runtime persists Failed. Tests cover
   Ready, Draining and Cancelling sessions alongside healthy work. Pending work
   is preserved; storage failures are not caught as session integrity failures.
2. Every known-unsent production batch refreshes Dataset settings before claim
   using the existing bounded GET. Retention checks the actual earliest pending
   timestamp against the current clock. Changed settings, elapsed retention after
   restart, explicit preflight retry, and a current batch from an expired session
   origin have regression coverage. No attempted publish is replayed.
3. Live controls return stored session status and readable UTC tag progress even
   when optional horizon detail cannot load. `horizonError` separately explains
   configuration/horizon damage. A successful pause stays successful in its
   response; storage/status corruption is not hidden by this fallback.
4. Division by zero and nonfinite arithmetic results have separate stable codes,
   structured locations, and corrective guidance without operand values. The
   arithmetic block now uses descriptive names and explicit comparison branches.
   A broader interpreter refactor is deferred to keep these semantic fixes small.
5. The archive guide documents database schema 7 separately from export format 2,
   horizon revision records and batch identity, retained SQLite revision history,
   and checksum-based compatibility with format-1 receipts. Host, manufacturing,
   and extension docs now describe the repaired behavior.

Validation: warning-free Release compilation; all **811 .NET tests** and **28
Python tests** passed. The 22 permanent cases in `AuditRepairTests` supplement
existing coverage. Independent checks passed all nine simulation examples and
six invalid schema cases, 100 gate scenarios (3722 samples), and both 72-hour
packaging/speed previews. The six original audit probes also pass after repair;
the runner restored the normal build afterward.

These are local macOS results. Windows/Linux CI has not run on these fixes;
earlier CI results apply to earlier commits. No live Historian writes, running
demo upgrades, multi-day soak, or fresh capacity measurements were performed.
Retention may change after a successful settings read, so that check is not an
acceptance receipt. The existing blind-publish, human pattern review, and
uncertain-delivery constraints remain unchanged.
